# Chapitre 11 — Déploiement Docker, scalabilité et mode queue

### 1. Préparer une instance n8n pour la production

Faire tourner n8n en production ne se limite pas à lancer une commande locale. L'instance doit être configurée avec des paramètres stricts pour garantir sa stabilité :

| Variable d'environnement | Valeur recommandée | Rôle technique indispensable |
| :--- | :--- | :--- |
| `WEBHOOK_URL` | `https://n8n.mondomaine.com/` | URL publique résolue pour la réception correcte des webhooks et des redirections OAuth2 |
| `N8N_ENCRYPTION_KEY` | Chaîne aléatoire de 32+ caractères | Clé de chiffrement persistante pour le trousseau de clés |
| `EXECUTIONS_DATA_PRUNE` | `true` | Active la purge automatique des anciennes données d'exécution |
| `EXECUTIONS_DATA_MAX_AGE` | `168` (7 jours en heures) | Supprime l'historique volumineux pour préserver l'espace disque |
| `DB_TYPE` | `postgresdb` | Remplace la base embarquée SQLite par PostgreSQL haute performance |

### 3. Scalabilité horizontale : Le mode Queue avec Redis et Workers

En mode standard (*Single Instance*), un pic soudain de 1 000 requêtes webhook simultanées peut saturer la boucle d'événements Node.js de l'instance principale.

Pour absorber des charges massives, n8n propose le **Mode Queue** :

<ArchitectureDiagram
  title="Architecture distribuée n8n en mode Queue avec Redis"
  diagram={`[ REQUÊTES WEBHOOKS ENTRANTES ]
                 |
                 v
      [ N8N MAIN / WEBHOOK INSTANCE ] (Ne fait qu'ingérer les requêtes)
                 |
                 v (Enfile les jobs)
          [ REDIS BROKER ]
           /           \\
          v             v
  [ N8N WORKER 1 ]  [ N8N WORKER 2 ]  [ N8N WORKER N ]
         \\             /
          v           v
    [ BASE DE DONNÉES POSTGRESQL & MYSQL ]`}
/>

- L'instance **Main** se contente d'accueillir les requêtes HTTP, de répondre en quelques millisecondes et de placer les tâches dans une file d'attente **Redis**.
- Des conteneurs **n8n Workers** indépendants dépilent les tâches de la file et exécutent les calculs lourds, les appels Gemini et les requêtes SQL.
- Si le volume de requêtes explose, il suffit d'augmenter le nombre de workers (`docker compose scale n8n-worker=5`).

### 4. Sauvegardes et politiques de rétention des exécutions

Pour éviter que la base de données interne n'atteigne plusieurs dizaines de gigaoctets en quelques mois, configurez la purge programmée :

<CodeBlock
  language="bash"
  title="Politique de sauvegarde automatique de la base n8n"
  code={`# Sauvegarde quotidienne de la base de données PostgreSQL
docker exec -t \$(docker ps -qf "name=postgres") \\
  pg_dump -U n8n_db_user n8n_production | gzip > backup_n8n_\$(date +%F).sql.gz

# Export régulier des workflows sous format JSON versionné
n8n export:workflow --all --output=/backups/workflows.json`}
/>
